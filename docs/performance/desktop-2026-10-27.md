Base: `master`, commit `bbb9efb`. Escopo: frontend React do desktop Tauri; nenhuma alteração no backend, banco ou linha SaaS.

## Coordenação adaptada do CLAUDE.md

Sol define as fatias e decisões de design, revisa os diffs e mede o resultado. Luna 6 High executa fatias delimitadas com contexto mínimo. Comandos verificam lint, testes e build. A execução foi autorizada pelo pedido do usuário; publicar branch/PR permanece uma etapa posterior à revisão.

Fatias implementadas sob revisão:

1. `src/App.tsx`: carregar páginas com `React.lazy`; `Layout.tsx` e `CounterLayout.tsx`: Suspense no conteúdo, mantendo navegação disponível e feedback acessível.
2. `package.json` e lock: remover somente dependências sem uso; expor comandos de medição.
3. `src/lib/pdf-service.ts`: carregar o motor PDF apenas na geração; preservar assinaturas, helpers e documentos.
4. `vite.config.ts`: agrupar ícones e separar o runtime React, reduzindo arquivos pequenos sem antecipar módulos de negócio.
5. `scripts/measure-bundle.mjs` e `scripts/measure-desktop.mjs`: medições reproduzíveis e relatório.

## Método

`measure-bundle.mjs` soma todos os JS emitidos (inclusive workers), CSS e o grafo recursivo de imports estáticos da entrada. Não confunde o tamanho de um arquivo com o custo inicial total. Gzip é calculado por arquivo, sem supor que todo o aplicativo seja baixado.

`measure-desktop.mjs` serve um build de produção feito com `VITE_E2E_MOCK=1`, usando o IPC de teste existente, em Chromium, viewport 1366×768, contextos novos e cache desabilitado. Mede cinco repetições para `/` e `/clientes`, nos perfis normal e CPU 4× mais lenta / rede 4 Mbps / latência 100 ms. Usa gzip e movimento reduzido, idênticos antes/depois. Mede até splash sair e título da rota aparecer, além de scripting, tarefas, heap e bytes JS/CSS. Também mede a primeira navegação interna para outra tela.

São benchmarks do frontend com IPC simulado e dados vazios. Não medem tempo de consulta PostgreSQL, inicialização Rust, custo de grandes bases reais, nem o WebView2 do Windows. No Tauri os assets são locais: a simulação de rede testa o carregamento frontend sob restrição; não demonstra melhora da conexão com o banco.

O splash mínimo obrigatório de 1100 ms e a animação foram preservados. Não foi usado um encurtamento artificial do splash para melhorar cold load.

## Trade-offs e limites

- Cada tela tem um custo no primeiro acesso, em troca de carregar menos código na abertura. O menu permanece disponível durante a espera; o fallback informa o carregamento via `role=status`.
- O carregamento sob demanda usa o cache de módulos do navegador, sem cache de dados de negócio nem mudança de política de permissões.
- A divisão em chunks pode aumentar a soma gzip de todos os arquivos por perder compressão compartilhada. O relatório apresenta o total, além da entrada, para deixar esse custo visível.
- O motor PDF é carregado no primeiro documento. O resultado e as operações de salvar/imprimir/enviar continuam sendo verificados pelos testes existentes.
- A rota POC foi preservada. Retirá-la apenas para diminuir o bundle alteraria funcionalidade; seus assets continuam no pacote distribuído.
- CSS existente foi preservado, sem remover estilos de foco, movimento reduzido ou telas secundárias para atingir uma pontuação.
- Desktop interno não é conteúdo indexável; não há mudança no portal público ou nos seus metadados/SEO.

## Reproduzir

```bash
npm ci
npm run build
npm run perf:bundle -- dist bundle.json
VITE_E2E_MOCK=1 npx vite build --outDir /tmp/autoos-mock-dist
# Requer Chromium instalado pelo Playwright ou CHROMIUM_PATH com caminho explícito.
npm run perf:desktop -- /tmp/autoos-mock-dist runtime.json
npm run lint
npm run test:run
npm run e2e
bash scripts/pre-qa-check.sh origin/master
```

Compare builds do commit-base e da branch no mesmo ambiente. Execute benchmarks sem testes/builds concorrentes. Os JSONs preservam as repetições individuais; compare medianas e examine regressões por rota, não só um agregado.

Bytes decimais, calculados sobre o mesmo build desktop. A carga estática inclui CSS e todo import estático transitivo, antes de carregar a rota ativa.

A meta de 50% foi superada no código inicial. Isso **não significa** reduzir em 50% todas as métricas ou o instalador. O volume total de JS não diminuiu; foi mantido para preservar os recursos, e o custo da fragmentação gzip foi aceito em troca da redução de carga inicial. Remover duas dependências já eliminadas por tree-shaking reduz instalação/manutenção, não o JS distribuído.

## Build

Antes do agrupamento final dos ícones: quatro builds completos alternados (`npm run build`, inclui TypeScript), sem testes ou builds próprios simultâneos:

| Execução | Base | Final |
|---|---:|---:|
| 1 | 81,18 s | 36,22 s |
| 2 | 72,13 s | 49,97 s |
| Mediana das duas observações | 76,65 s | 43,09 s |

Não apareceu regressão de build nessa comparação (−43,8% na mediana). A dispersão é alta neste host compartilhado e são somente duas observações por versão: não usar isso como promessa de ganho no CI. As primeiras execuções exploratórias foram 43,61 s na base e 55,91 s no final, motivo para repetir a comparação. Não houve mudança na configuração de build ou desativação de checagens.

O build completo com a configuração final de ícones passou em **34,16 s** (TypeScript + Vite; Vite 17,52 s), sem aviso de dependência circular. O agrupamento final adicionou 2.660 B gzip à entrada em comparação com rotas/PDF apenas, mas removeu seis arquivos JS e reduziu 4.897 B da soma gzip de todo JS. O grafo inicial permanece restrito a entry, runtime React, ícones e CSS: não inclui PowerSync, PDF ou gráficos. Foi descartada a configuração `onlyExplicitManualChunks: true`, que deixava helpers CommonJS no entry e gerava ciclos; a configuração entregue inclui os helpers junto das dependências dos grupos.

## Validação funcional

- TypeScript/lint e build desktop final passaram. Nenhuma mudança em Rust, migrações, autenticação, permissões ou política de dados.
- Testes focados de PDF e divergência: 72/72 passaram, incluindo geração real de documentos em memória e fluxo de prévia/salvar/enviar.
- Suíte completa frontend: 816/820 passaram inicialmente; os quatro restantes excederam 5 s durante builds concorrentes, em três arquivos. Repetição isolada dos três arquivos passou 49/49, sem editar testes, aumentar timeout ou desativar casos. A base também apresentou timeout em um teste durante concorrência, que passou isolado.
- Testes do updater/manifest/normalização: 15/15 passaram.
- Playwright contra o **build de produção** com IPC simulado: 6/6 passaram em 32,4 s. Valida balcão em resoluções desktop, cobertura do splash, navegação e formulário de CPF duplicado. O vídeo foi desligado apenas na configuração temporária do runner por falta de ffmpeg no host; os casos de teste permaneceram iguais.
- Inspeção visual em Chromium 1366×768 confirmou menu, filtros, ações e layout preservados.
- O harness de benchmark instala stubs de registro de eventos Tauri, além do IPC já simulado, para a navegação não gerar erros artificiais do ambiente web. Exceções de página fazem o benchmark falhar. Os assets são pré-comprimidos antes das amostras, excluindo o custo de gzip do servidor das medições de abertura.

Tauri nativo, WebView2 Windows e PostgreSQL real não foram executados neste host. Não é uma certificação de performance de rede/banco ou de grandes bases reais. O PR deve preservar essa distinção.

A primeira navegação medida é Dashboard → Clientes, ou Clientes → Equipamentos. A troca real é explícita: Clientes → Equipamentos passou de 101,0 para 148,4 ms em desktop normal (+47,4 ms), e de 364,2 para 1.025,2 ms no perfil limitado (+661,0 ms). Dashboard → Clientes passou de 65,5 para 98,3 ms no perfil normal e de 202,2 para 541,8 ms no limitado. O menu permanece operacional e há feedback acessível durante a espera. No Tauri os chunks são locais, então o perfil de rede simulada não representa o transporte de assets do instalador. Não houve prefetch indiscriminado de outras telas para esconder esse custo.
